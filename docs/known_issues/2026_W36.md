# Known issues — 2026 week 36

> Monday 2026-08-31 to Sunday 2026-09-06.

All five came out of running `spij` end to end against a local Qdrant + PostgreSQL
(105 documents, 563 chunks, 2026-09-01 to 2026-09-03). `status` is deliberately not
here: it is the same problem for every source and lives in
[`2026_W30.md`](2026_W30.md) ("`status` is written in two languages…").

## spij harvests newest-first with no filter, so the corpus fills with minor administrative acts

> **Live** · strategy, not code — the filter exists and is unused
> **Detected:** 2026-09-03 · **Last verified:** 2026-09-08 against `3e2a7e5`

The crawl starts at cursor 0, which SPIJ serves most-recent-first, and the
`dispositivoLegal` filter defaults to empty (`src/modules/spij/config/index.ts:41`).
Of the 105 documents that came in:

- 49 `RESOLUCION MINISTERIAL`, 11 `ORDENANZA`, 9 `RESOLUCION VARIAS`,
  5 `RESOLUCION DIRECTORAL`, 5 `RESOLUCION SUPREMA`, 4 `DECRETO SUPREMO`.
- **0 `LEY`, 0 `DECRETO LEGISLATIVO`, 0 `CODIGO`.**
- 82 of 105 classified as *Derecho administrativo*: appointments, travel
  authorizations, tariff updates.

SPIJ reports 878,796 documents. At this order the corpus is full of "Designan
Gerente…" long before the Código Civil enters — and a lawyer asking *"qué normas me
ayudan en este caso"* gets the appointment of a manager as top result. No embedding
tweak fixes a corpus made of the wrong documents.

What to implement: a harvest order by `dispositivoLegal` — leyes, decretos
legislativos, decretos supremos, códigos and TUOs first, resoluciones last — as lanes
on `SPIJ_DISP`, written into the runbook. It needs no new code.

## One spij chunk in three starts mid-sentence

> **Live** · measured, not estimated
> **Detected:** 2026-09-03 · **Last verified:** 2026-09-08 against `3e2a7e5`

On 300 real chunks from the local Qdrant, 107 (35 %) begin mid-sentence:
*"…como, deben implementar el Sistema Local de Gestión Ambiental"*,
*"…la presente Ley, los Planes para el Acondicionamiento Territorial"*. The lawyer
receives half an article as context, and the vector of that chunk carries half a
meaning.

Two causes, both in `src/services/ingest-local/chunk.ts`:

- Splitting is **per page** (`chunk.ts:178`): the 250-character overlap never crosses
  a page boundary, so every page break is a hard cut. For spij the pages are
  **artificial** — they are puppeteer's pagination of an HTML document (see the next
  section), so the cuts fall anywhere.
- The splitter is `RecursiveCharacterTextSplitter` at 1800/250
  (`chunk.ts:11-12`, `:169`). It knows nothing about `Artículo N.-`, incisos or
  disposiciones: an article is cut wherever the count lands.

What to implement: article-aware splitting for norms with structure (one chunk = one
article, the unit a lawyer cites), and no hard cut at page boundaries when the pages
are synthetic. Depends on the next section: the article structure is in the HTML
and is degraded by the PDF round trip.

## spij's text takes a round trip through a PDF it generates itself

> **Live** · lossy and slow, and the origin of the synthetic pages above
> **Detected:** 2026-09-03 · **Last verified:** 2026-09-08 against `3e2a7e5`

SPIJ delivers the norm as clean HTML. The module renders it to PDF with puppeteer
(`src/modules/spij/utils/ingest/index.ts:175`) and the local ingest extracts the
text **back out of that PDF** (`src/services/ingest-local/index.ts:103`,
`extractPages(pdfBytes)`), then chunks it. Every run prints the font-substitution
warnings of that extraction.

The PDF is only needed for S3 and for a human to open. For vectorizing, the HTML is
strictly better: it keeps `Artículo 3.-`, headings and incisos, has no pages, and
skips a puppeteer render per document.

What to implement: a text entry point in `ingest-local` that takes the HTML (or
plain text) for chunking and the PDF only for the S3 upload. `extractPages` stays
for sources that genuinely deliver PDFs.

## Every spij document is `normative`, so nothing ever gets article-level chunking

> **Live** · crosses into the assistant
> **Detected:** 2026-09-03 · **Last verified:** 2026-09-08 against `3e2a7e5` (scrapping) and `73e0675` (assistant)

`src/modules/spij/utils/metadata/index.ts:64` maps `tipoNorma = "NR"` to
`normative` regardless of the `dispositivoLegal` SPIJ already gives us. The only type
that triggers article chunking in the assistant is `codigo`
(`app/modules/legal_documents/ingest/service.py:53`,
`_CODE_DOCUMENT_TYPES = frozenset({"codigo"})`), and the local ingest has **no
article splitter at all** (only the character splitter of the previous section).

So when the Código Civil, Penal or Procesal come in — the most cited documents in
the corpus — they will be cut blind at 1800 characters, in both ingestion routes.

What to implement: map `dispositivoLegal` → `type` in spij (`CODIGO` → `codigo`, the
rest stays `normative`), which is a few lines; and bring article splitting into
`ingest-local` so the local route matches the assistant's.

## Re-ingesting spij duplicates every document already in production under the old `source_url`

> **Live** · a trap no gate catches — count in production **not verified**
> **Detected:** 2026-09-01 · **Last verified:** 2026-09-08 against `3e2a7e5`

The document identity is `uuid5(country + source_url)`
(`src/services/ingest-local/ids.ts:18`): same URL, same id, re-ingest replaces.
Commit `e615f75` (2026-09-08) changed spij's `source_url` from the internal API
endpoint (`…/spij-ext-back/api/procesarword/<id>`, which answers 401 to a lawyer)
to the public portal page (`…/spij-ext-web/#/detallenorma/<id>`). That was the
right fix — but every spij document **already in production** with the old URL now
gets a **new** id on re-ingest: it is duplicated, not replaced, and its old Qdrant
points stay behind as orphans.

How many there are is unknown: this was found from a local environment and
production was deliberately not touched. Before the first spij run against
production:

1. Count them:
   `select count(*) from documents where source_url like '%spij-ext-back/api/procesarword/%';`
2. If the count is small, delete those rows and their Qdrant points
   (`metadata.document_id` filter) and let the re-ingest recreate them.
3. If it is large, migrate: recompute `document_id` from the new URL and rewrite the
   PostgreSQL row, the `legal_document_entities` links and the Qdrant point payloads.

Running spij against production before this is done grows the corpus with
duplicates that no ledger will ever detect — the ledger only knows the SPIJ id, not
the URL it was ingested under.

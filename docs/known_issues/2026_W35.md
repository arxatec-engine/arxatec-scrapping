## The production legal corpus is still writable without a credential

> **Live** · this is **IC-1**, and it is the same problem as the assistant's **V-1** / **QL-1** / **ASST-01**
> **Detected:** 2026-08-25 · **Last verified:** 2026-08-25 against `faf490e`, from the VPS deployment
> Full evidence: `git show 3792b14:docs/registro/2026-08-25/INGESTA_SIN_CREDENCIAL.md`

During the 2026-08-25 deployment, production's nginx log showed writes and deletes
against the legal corpus **with no credential, over the public domain**, in
progress (the corpus went from 23,713 to 30,644 points during the session):

```text
38.211.62.41  qdrant-js/1.17.0
  PUT  /collections/legal_documents_pe/points
  POST /collections/legal_documents_pe/points/delete
```

The client is **this repo** — identified by version: this repo declares
`@qdrant/js-client-rest@~1.17.0`, the service declares `1.16.2`, the assistant uses
the Python client. And it explains why the assistant's V-1 had been open for a
month: closing Qdrant would have broken ingestion, because the client was built
with no `apiKey` and no variable to put one in.

**That part is fixed**: `QDRANT_API_KEY` exists now
(`src/services/ingest-local/config.ts:30`, optional, verified 2026-09-08). It must
hold the same value as the assistant's `QDRANT_API_KEY` and the service's
`QDRANT_LEGAL_API_KEY` — three names, one key.

What is still live is the corpus itself, and the order matters:

1. Deploy this repo wherever ingestion runs.
2. Put `QDRANT_API_KEY` in its `.env`, same key as the assistant.
3. **Only then** close V-1 on the VPS.
4. Smoke it: `pnpm verify <source>` and confirm it still writes.

Done the other way round, ingestion dies and the corpus stops growing **with no
alarm** — it would show up days later as a corpus that is not advancing.

## Ingestion writes to production over the public internet, in the clear

> **Live** · this is **IC-2**
> **Detected:** 2026-08-25 · **Last verified:** 2026-08-25 against `faf490e`

Even with the credential in place, the traffic goes over the internet through the
public domain. The healthy shape is a private network or a tunnel.

It is not fixed by this repo alone — it is infrastructure — but it is recorded here
because this repo is the client that makes the calls.

## Ingestion can delete from production by design

> **Open decision, not a defect** · this is **IC-4**
> **Detected:** 2026-08-25 · **Last verified:** 2026-08-25 against `faf490e`

`POST /points/delete` against production from a laptop is possible by design. With
the credential in place there is at least a distinction between our traffic and
somebody else's, but the capability remains.

Whether ingestion should be able to delete at all is worth deciding. Until it is
decided, assume any local run with the production credential can remove points.
